## Findings

### M360-1 — Aurora downsizes memory-optimized DB classes on CPU alone (C18 / C10) — HIGH

Both counted Aurora recs — **$2,372.50/mo, 49% of the entire headline** — cut a
memory-optimized database's RAM on a CPU-only signal:

| Instance | Change | RAM | Gate | Counted |
|----------|--------|-----|------|---------|
| `prod-360vuz-db-writer` | db.r6g.4xlarge → **db.r6g.large** | 128 → **16 GiB** | avg CPU 2%, peak 10% / 14d | $1,509.64 |
| `prod-integrations` | db.r6g.4xlarge → db.r6g.2xlarge | 128 → 64 GiB | avg CPU 5%, peak 31% / 14d | $862.86 |

Rates and arithmetic are EXACT (table above) — the defect is **evidential**, the
same class as AFS-1 (af-south-1) but in a different adapter. `rightsize_target_size`
(`services/aurora_logic.py:104`) is purely
`required_vcpu = current_vcpu × peak_cpu_pct / 100 × 1.2`; memory is never
consulted. On the first instance that yields 16 × 0.10 × 1.2 = 1.92 vCPU, so it
recommends dropping **eight rungs** and **8× the RAM**.

**Three things make this worse than AFS-1:**

1. **For a database, memory IS the product.** Aurora's buffer pool holds the
   working set; low CPU alongside a large buffer pool is the signature of a
   well-cached database, not an idle one. Cutting 128 GiB to 16 GiB would
   collapse the cache-hit ratio and can degrade a *production writer* badly
   while CPU still reads 2%.
2. **The evidence is FREE here.** Unlike EC2 — where `mem_used_percent` needs
   the CloudWatch agent, which is why AFS-1 could only demote — AWS publishes
   **`FreeableMemory`** for every RDS/Aurora instance with no agent at all, plus
   `BufferCacheHitRatio` for Aurora MySQL. `grep -rn "FreeableMemory" services/`
   returns **nothing**: the metric has never been read.
3. **The repo already knows how.** The ElastiCache adapter gates the identical
   lever on `PeakMemoryUsagePct <= 35%` AND zero `Evictions`, and publishes that
   reasoning in its `AuditBasis`. Aurora needs the same shape, not a new idea.

- Suspect: `services/aurora_logic.py:104` (`rightsize_target_size`),
  `services/adapters/aurora.py:187` (emit).
- **FIXED 2026-08-11.** Because the evidence is obtainable this **gates** rather
  than merely demoting. `instance_memory_gib` derives class RAM from a family
  ratio (r 8 / m 4 / x 16 GiB per vCPU — memory scales linearly WITHIN a family;
  burstable `t` and `c` are deliberately absent because t-family memory is not
  linear in vCPU, so they return None and withhold the lever rather than guess).
  `memory_floor_size` is the memory counterpart of the CPU floor, and
  `combined_rightsize_target` takes the LARGER of the two, returning None when
  memory cannot be established at all. The adapter reads
  `AWS/RDS FreeableMemory` at **Minimum** over the window — the safe target is
  the one that still fits at the instance's most memory-hungry moment, so an
  average would understate the working set.
- `rightsize_target_size` is left pure and CPU-only, exactly as AFS-1 left
  `_classify_utilization` alone: the verdict still says what the CPU shows, and
  the caller composes the floors.
- **Gating beats demoting here.** Where memory binds *above* the CPU floor but
  still below the current class, the result is a smaller-but-honest downsize
  rather than nothing — e.g. a 512 GiB class at 10% CPU holding 100 GiB lands on
  4xlarge instead of the CPU-only 2xlarge. A withheld lever emits a `ctx.warn`,
  so it is disclosed rather than silent.
- The memory evidence rides on the card (`PeakMemoryUsedGiB`, `TotalMemoryGiB`,
  and in `current_value`/`reason`), so a reader can see WHY shrinking a
  database's RAM is safe.
- Verified delta, simulated against this scan's JSON: both recs lose their
  target for want of evidence, **−$2,372.50 → headline $2,468.56**. On the
  re-scan `FreeableMemory` will be readable, so any instance with genuine
  headroom counts again — legitimately, with the evidence attached. **The
  re-scan headline is therefore expected to land between $2,468.56 and
  $4,841.06**, and which it is, is itself the finding's answer.

### M360-3 — OpenSearch downsizes heap-bound nodes on CPU alone (C18) — HIGH (unexercised here)

Withdrawing M360-2 prompted a sweep of every adapter that decides a downsize from
CPU. Results:

| Adapter | Binding dimension | Verdict |
|---------|-------------------|---------|
| `ec2.py` | memory | FIXED (AFS-1) |
| `adapters/aurora.py` | memory | FIXED (M360-1) |
| `elasticache.py` | memory | **already correct** — peak `DatabaseMemoryUsagePercentage` <= 35% AND zero evictions |
| `containers.py` (ECS) | memory | **already correct** — `avg CPU < 20% AND avg memory < 30%`, returns None if either metric is missing |
| `dms.py` | — | idle/oversized levers, not a CPU-driven one-size-down |
| `opensearch.py` | **JVM heap** | **DEFECTIVE** |

`services/opensearch.py:235` emits "Underutilized Domain" on
`avg CPU < LOW_CPU_THRESHOLD` alone, and `services/adapters/opensearch.py:510`
prices it as a one-size-down node delta that stays **COUNTED** whenever the delta
prices (only an unpriceable target or CoH coverage demotes it).

An OpenSearch data node is heap-bound — the JVM holds field data, indices and
caches, and one rung down halves the node's RAM and therefore its heap. Low CPU
is the normal profile of a search cluster serving from a warm heap.

It did **not** fire on this account (no OpenSearch tab), so there is no dollar to
attribute — but the defect is live for any account that has one.

- **FIXED 2026-08-11.** Gated on `JVMMemoryPressure` (free on `AWS/ES`, no
  agent), read at **Maximum** — a node must hold its heap at the domain's most
  pressured moment. `MAX_JVM_PRESSURE_PCT = 37.5` is **derived, not invented**:
  halving the heap roughly doubles pressure and AWS treats sustained pressure
  above 75% as GC territory, so the bound is half of that — the same reasoning
  ElastiCache used for its 35%. An unreadable metric withholds the lever and
  emits a `ctx.warn` (C18).
- Predicted delta on this account: **$0.00** (lever did not fire).
