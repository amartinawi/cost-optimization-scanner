## NEW defects found

### LS-1 — WITHDRAWN 2026-08-10. The premise was wrong.

**This finding was incorrect and is retained only as a record.** It claimed
Savings Plans cover "EC2 / Fargate / Lambda / SageMaker only". That is the
pre-December-2025 coverage matrix. **Database Savings Plans went GA 2025-12**
and cover DynamoDB, RDS/Aurora, ElastiCache, OpenSearch, Neptune, DocumentDB,
Keyspaces, Timestream and DMS. Verified two independent ways:

* live enum — `ce:GetSavingsPlansPurchaseRecommendation` with a bogus type
  returns `Member must satisfy enum value set: [DATABASE_SP, SAGEMAKER_SP,
  COMPUTE_SP, EC2_INSTANCE_SP]`;
* live offering rates — Database SP offerings return 432 rates with
  `serviceCode=AmazonDynamoDB`, 28,892 for RDS, 3,609 for OpenSearch.

So the DynamoDB recommendation was **correct advice**, not a false positive.

Worse, the proposed fix would have caused the damage it was meant to prevent.
**Cost Explorer already pre-filters `GetSavingsPlansCoverage` to SP-eligible
services** — this account has 23 CE SERVICE values and the call returned 3, all
eligible. An allowlist therefore adds zero precision and only subtracts recall;
built from the matrix above it would have silently disabled the check for
RDS and Aurora, the largest uncovered spend in most real accounts.

Lesson: a coverage/eligibility matrix is a *dated fact*, not a stable one. Verify
it against a live enum or offering-rate query before gating on it.

### LS-1 (original text, superseded) — `SP Coverage Gap` emitted for services Savings Plans cannot cover

`services/adapters/commitment_analysis.py:285` `_check_sp_coverage` emits a gap
rec for whatever `SERVICE` Cost Explorer returns, with **no SP-eligibility
allowlist**. Confirmed live by direct API call:

```
SERVICE='AWS Lambda'                              OnDemandCost=0.0
SERVICE='Amazon DynamoDB'                         OnDemandCost=0.00015950
SERVICE='Amazon Elastic Compute Cloud - Compute'  OnDemandCost=13.365118665800001
```

Savings Plans cover **EC2 / Fargate / Lambda / SageMaker only**. DynamoDB has
*reserved capacity*, an entirely different product. The rendered advice —
"Amazon DynamoDB has 0.0% SP coverage (below 80% threshold)" — is unactionable:
there is no Savings Plan to buy.

Harmless on this account only because `od` rounds to $0. On an account with real
DynamoDB spend the rec attaches a fabricated `0.30 x spend` figure to a product
that cannot be purchased. Same class as the CoH `type_map` keys that were not
real `ResourceType`s (tranche 4).

**Fix:** allowlist the SP-eligible CE SERVICE values before emitting.

### LS-2 (HIGH) — the flat 30% SP discount is ATH-1's `0.75` in another costume

Same function: `potential = od * (1.0 - rate) * AVG_SP_DISCOUNT_RATE` where
`AVG_SP_DISCOUNT_RATE = 0.30`, and the rec's own reason string admits
"verify against live offering rates".

A fabricated fraction with no account-specific input is precisely the ATH-1
defect (CRITICAL, closed in tranche 11). It survives here only by accident:
`_advisory_line` (`reporter_phase_b.py:68`) looks up `AdvisoryEstimate` and
`PotentialMonthlySavings`, but this rec stores its figure under
`monthly_savings` — so the renderer **silently drops it**. On this account the
EC2 rec carried ~$4.01 that never reached the card.

A **third** defect sits in the same expression: `(1.0 - rate)` double-discounts.
CE's `OnDemandCost` is *already* the uncovered residue — the repo's own
live-pinned fixture proves `TotalCost == OnDemandCost +
SpendCoveredBySavingsPlans` and `CoveragePercentage == covered / TotalCost`. On
that row ($200 uncovered at 88.9%) the old formula reported $22.20, a 9x
understatement.

**RESOLVED 2026-08-10 — the emission is deleted, not repaired.**

The obvious repair (carry the measured uncovered on-demand spend instead) was
rejected under adversarial review: CE documents `OnDemandCost` as the cost of
usage *at the public On-Demand rate* — a rate equivalent, not billed spend —
and this query carries no region filter. Live, the EC2 row reads $13.37 while
actual unblended on-demand was ~$0.0000009 (free tier). Surfacing it would
contradict the **"Uncovered On-Demand ($/mo)" stat card on the same tab**, which
is built from `UnblendedCost` filtered by REGION and PURCHASE_TYPE. That
replaces a hidden fabrication with a visible contradiction.

With the projection gone the card carries no dollar at all — a service name, a
coverage percentage, an "80%+" target. That is the LS-4 best-practice-nudge
class, which this project's scope forbids. So the emission is removed, matching
the MediaStore and OpenSearch precedents. The accumulators stay, so the honest
signal survives as the **SP Coverage stat card**.

`AVG_SP_DISCOUNT_RATE` and `COVERAGE_GAP_THRESHOLD` are deleted; both were used
only by the removed block.

**Consequence, accepted:** `html_report_generator.py:2507` drops any service with
zero rendered cards, and on this account `sp_coverage_gaps` held all 3. The
Commitment Analysis tab therefore disappears here, taking its stat cards with
it. On an account with real commitments the other five sources keep it alive.
Manufacturing a card to hold a tab open would reintroduce the noise being
removed.

### LS-7 (HIGH) — RESOLVED 2026-08-10. Database SP coverage was unattributed.

`services/commitment_scenarios.py:77` is
`SP_TYPES = ("COMPUTE_SP", "EC2_INSTANCE_SP", "SAGEMAKER_SP")` — no
`DATABASE_SP`. With the coverage-gap card removed, an account with large
uncovered DynamoDB / RDS / Aurora / ElastiCache / OpenSearch spend now gets
**complete silence**: no coverage card (deleted above) and no purchase card
(that plan type is never fetched).

This is the backfill that makes the LS-2 deletion whole, and it is strictly
better than the card it replaces — CE's purchase recommendations carry
AWS-computed dollars rather than a flat fraction.

Not bundled into the LS-2 fix because it needs its own verification: Database SP
ships a **1-year No-Upfront term only**, so the existing 2-term x 3-payment
matrix cannot be fanned out blindly — each invalid combination is a wasted
$0.01 CE call. `SP_TYPES` is pinned by `tests/test_commitment_scenarios.py:123`
and the module docstring advertises "SP (3 types)".

**Resolution.** Everything below is from a live probe, not documentation (C14):

* CE's `SavingsPlansType` enum really does carry `DATABASE_SP` (botocore
  1.43.47 service model) — so the type is fannable.
* `savingsplans:DescribeSavingsPlansOfferings` returns, per plan type:
  Compute / EC2Instance / SageMaker = all 6 combos; **Database = 1** (1yr, No
  Upfront). The fan-out is now derived from that probe (a free call) rather
  than the hardcoded fact, so a term AWS adds later is picked up without a code
  change. Fail-open by omission: an unresolvable probe requests the full matrix,
  because losing the probe must never lose the recommendation — that is the
  LS-7 defect itself.
* CE does **not** reject the 5 impossible combos; it accepts them and returns
  empty (verified, $0.02). So the restriction is not only worth $0.05/scan — it
  also stops the report rendering a purchase card for a plan nobody can buy, if
  CE ever did answer for an unsold term.
* The scenario grid always draws 2 terms x 3 payments, so the Database card
  carries a note (built from the probed combos) saying the blank cells are
  unpurchasable rather than unknown.

`projected_savings` gains a third non-overlap group mirroring the compute one:
`max(Database SP, sum(RDS/ElastiCache/OpenSearch/DynamoDB RIs)) + Redshift RI`.
Redshift stays additive because it is absent from the plan's productTypes —
folding it into the `max()` would under-count a real saving.

No `_COH_SP_MATCH` entry was added: the Cost Optimization Hub `ResourceType`
enum has no `DatabaseSavingsPlans` member, so a key would be an orphaned bucket
that can never receive a rec.

### LS-8 (HIGH) — RESOLVED 2026-08-10. An active Database SP demoted nothing.

Found while scouting LS-7, and strictly more severe than it: LS-7 is a missing
advisory, LS-8 was a **counted-dollar overstatement**.

`services/commitment_coverage.py:_fetch_savings_plans` branched on `Compute` /
`SageMaker` / `EC2Instance` and nothing else, so a `Database` plan matched no
branch and fell through. `CommitmentCoverage` had no field for it, and
`covers_rds` / `covers_elasticache` / `covers_opensearch` / `covers_dynamodb`
consulted Reserved-Instance sets only. On an account holding a Database SP that
already absorbs the spend, no C6 demotion fired and the CoH/Compute-Optimizer
rightsizing dollars — quoted on an **on-demand basis** — stayed COUNTED while
being unrealizable. The same defect the repo already fixed for Compute SP,
SageMaker SP and RIs, reopened by the Database SP launch (GA 2025-12).

Scope taken from the live offering record, not documentation
(`savingsplans:DescribeSavingsPlansOfferings`, offering
`bf9234b3-5784-4a5e-9ef4-29095d898aaf`): `productTypes` = RDS, DynamoDB, DSQL,
Neptune, DocDB, ElastiCache, Timestream, Keyspaces, DMS, OpenSearch.
**Redshift is absent**, so `covers_redshift` is deliberately left alone —
demoting a Redshift rec on this flag would under-count a real saving. The
offering carries no `region` field (like Compute), so the flag is a plain global
boolean rather than a region-scoped set.

Two further defects surfaced while fixing it, both pinned by regression tests:

* **The gate would have made the fix inert.** `want_sp` was
  `selected & {"ec2","lambda","containers","sagemaker"}` — the COMPUTE set. None
  of the services a Database SP covers appear in it, so a scan of only database
  services never read the plans and `has_database_sp` stayed False on exactly
  the accounts the fix targets. Now gated on
  `_COMPUTE_SP_SERVICES | _DATABASE_SP_SERVICES`.
* **The SP pager could not terminate.** It looped on `if not token: break`,
  with no guard against a non-string or repeated `nextToken` — unlike the CE
  pager, which has carried that guard (and a test) since an earlier tranche.
  Latent while the read was compute-gated; widening the gate made it reachable
  on many more scans. Same guard now applied.

Deliberate imprecision, in the safe direction: the plan's rates reach only Gen7+
RDS families, Valkey-era ElastiCache nodes and Graviton OpenSearch, but the
boolean demotes every family of a covered service. Over-demotion under-counts,
which the tie-break rule prefers to any risk of overstating.

### LS-3 (MEDIUM) — RESOLVED 2026-08-11. Gated on NAT presence, per VPC.

`services/vpc_endpoints.py:69,79`. The check emits "Create S3/DynamoDB Gateway
endpoint **to reduce NAT Gateway costs**" whenever a VPC lacks the endpoint,
with no NAT gate and no traffic gate.

Verified live: **0 NAT gateways in the account**, only the default VPC, and both
cards were still emitted. With no NAT there is no data-processing charge to
avoid, so the saving is structurally $0 — the stated mechanism does not exist.

Every AWS account has a default VPC with no gateway endpoints, so this emits
**2 permanent noise cards on every scan of every account in every region**.

**Fix (applied):** gated on at least one available NAT Gateway **in that VPC**.
The NAT->VPC map is already resolved by the adapter for CoH attribution, so
the gate costs no extra API call. A FAILED NAT enumeration passes `None` and
leaves the check ungated — a failed read is not evidence of absence, and
silently deleting a finding is the harder failure to notice.

Live re-check on the same account: **2 cards -> 0**.

### LS-4 (MEDIUM) — RESOLVED 2026-08-11. One measured, one deleted.

CLAUDE.md: scope is strictly cost; every rec must produce a concrete
account-specific $ saving. Two rendered blocks do not:

* **"Never-Expiring Log Groups" (21 resources)** — "Set retention policy to
  prevent unlimited log growth", $0.00, no figure. This is *both* a scope
  violation and a **false negative**: CloudWatch Logs publishes `StoredBytes`
  per log group, so `stored_GB x archived-storage rate` is a real measurable
  account-specific dollar. Currently a pure nudge.
* **"Versioning Optimization" (22 buckets)** — "Monitor versioning growth",
  $0.00, "quantify via S3 Storage Lens". "Monitor X" delegates the analysis
  back to the user; it is not a recommendation with a dollar.

Same call as the deleted OpenSearch version-upgrade nudges and the MediaStore
EOL notice.

**Resolution — and a correction to this finding.** The claim that
`stored_GB x archived-storage rate` is "the missing dollar" is **wrong**, and
the code already refuted it (monitoring H2): setting a retention policy deletes
only data OLDER than the chosen window, and `describe_log_groups` exposes no age
distribution, so charging 100% of `storedBytes` fabricates a saving that scales
with the largest groups. That is the same class of error as ATH-1's `0.75` and
FS-2's stock-minus-flow. The figure is the log group's **cost**, not its saving.

There is, however, a provable subset. If the ingestion read SUCCEEDED and
reported no bytes at all across the window, every stored byte already predates
that window, so setting retention to it deletes all of them and 100% of the
storage cost is genuinely realizable. Live-verified polarity (2026-08-10):
`AWS/Logs IncomingBytes` publishes only when data arrives, and `GetMetricData`
returns `StatusCode=Complete` with an EMPTY `Values` list for a silent group —
so "proven silent" is distinguishable from "not measured". That distinction is
the whole basis of the counted dollar, and a test pins that an unanswered query
(not probed / throttled / `--fast`) never counts.

So the log-group check now splits three ways:

* proven silent -> **COUNTED** at the full storage cost;
* measured or unmeasured otherwise -> `$0` advisory that now carries the storage
  cost as an explicit **ceiling** (answering the "no figure" half of this
  finding — it is no longer a bare nudge);
* either way, suppressed entirely when the figure rounds to `$0.00`, because a
  card whose own dollar renders as zero refutes itself — the LS-5 defect. The
  live account's 21 never-expiring groups were Lambda logs of a few KB each,
  ~$0.0000006/mo.

The ingestion probe this rests on was already being made (MON-3), so the counted
lever costs no new API call.

**Versioning Optimization is deleted**, with its per-bucket
`get_bucket_versioning` call. It fired on versioning being ENABLED, never on any
measured noncurrent bytes, so it could not tell a bucket wasting money on old
versions from one with none. Noncurrent bytes are not obtainable from any free
API: CloudWatch `BucketSizeBytes` folds them into the per-storage-class totals,
and only S3 Storage Lens ADVANCED metrics break them out. The card could only
ever say "go measure this yourself".

Live re-check on the same account: **21 cards -> 0** (log groups), **22 -> 0**
(versioning).

### LS-5 (LOW) — RESOLVED 2026-08-11. The card is deleted.

S3: *"Empty bucket older than 171 days - consider deletion. $0.00/month - empty
bucket incurs no storage cost."* The card states its own saving is zero
**because the resource is free**. Should not be emitted.

**Resolution.** Deleted outright, unlike LS-3 and LS-4: there is no lever here
to gate or quantify. An empty bucket bills nothing, so deleting it saves
nothing. Its `unused_buckets` descriptor went too — it promised "100% of bucket
costs" for deleting a bucket whose costs are $0. Incomplete multipart-upload
parts DO bill and are invisible to `list_objects_v2`, but they belong to the
`multipart_uploads` check, which carries a real dollar and is pinned by a
regression test so it is not collateral damage. Dropping this also removes a
`list_objects_v2` call per bucket that existed only to feed it.

Live re-check: 1 empty bucket of 23, so 1 card -> 0. With LS-4's versioning
deletion, `get_enhanced_s3_checks` now emits **nothing at all** on this account
(was 23 cards, every one of them $0).

### LS-6 (LOW, report copy) — RESOLVED 2026-08-11. The advisory count is published.

Exec summary renders "No Cost Optimization Recommendations Found — Your AWS
resources appear to be well-optimized" while 52 advisory cards render below it,
and the footer reads "Report covers 4 AWS services with 0 optimization
recommendations". Internally correct (both numbers are the *counted* count) but
reads as a contradiction. The advisory count should appear in both.

**Resolution.** The headline stays COUNTED-only — that semantics is right and is
not what was broken. What was missing is that the report had no way to *say*
what the cards below it were. `summary.total_advisory_recommendations` now
carries that number, and both the executive summary and the footer read from it.

With advisories present, the empty state no longer claims the account is
"well-optimized" — an affirmative claim the scan did not make. It now says no
recommendation resolved to a concrete account-specific dollar, and that the N
advisory findings below each name a real cost lever whose saving could not be
sized from the available data. A genuinely clean account (0 counted, 0 advisory)
still gets the original message.

The count is computed DIRECTLY (`Counted is False` and not `OPTIMIZED`), never
as `rendered - counted`: a rec that is somehow both counted and OPTIMIZED makes
that subtraction negative, and the report would print "-2 advisory findings".
A test pins that, and it fails with `-1` / `-2` against the subtraction version.

### LS-9 (LOW, filed 2026-08-11) — the static-website CloudFront nudge

Noticed while removing LS-5's card; it is the next emission in the same function
and the same class as LS-4/LS-5, but out of that tranche's scope so it is filed
rather than fixed.

`services/s3.py` "Static Website Optimization": *"Static website detected: Enable
CloudFront CDN for reduced data transfer costs and improved performance"*,
`$0.00/month - data transfer dependent (CloudFront CDN)`. Two problems:

* **No dollar, and no path to one from this data.** The saving is the S3-egress
  vs CloudFront-egress delta on bytes served, which needs per-bucket egress GB.
  `BucketSizeBytes` is a stock, not egress; `AWS/S3` publishes no egress metric.
  CloudFront pricing is also tiered and region-class dependent, so even with GB
  the sign is not obvious for small volumes.
* **"improved performance" is explicitly outside the strictly-cost scope**, and
  it is the half of the sentence that actually justifies the change.

Did not fire on this account (no static-website buckets), so it did not appear
in the 52. Same call as the deleted OpenSearch version-upgrade nudges, the
MediaStore EOL notice, and LS-4/LS-5 — but verify against a live account that
has one before deleting, in case egress is obtainable some other way.
